roadmap was reviewed. Source and library reference: mise Odin

## Observations and reproduced counterexamples

`commands.odin` renders `claude_md` from `applicable_topics`. Milestone 3 already
shares `check_applies` between enforcement and topic selection. Topics and rules
are sorted when loaded; disabled/retired rules are removed; reader advice has its
own topic role filter. Whole-project output is the union of applicable rules over
discovered packages, not the claim that every rule applies to every package.
Path output selects exactly one package but currently does not label that selected
package in the generated text. The catalog for an empty project is explicitly
conditional.

Existing guidance asks for regeneration after editing `rules/`, which is incomplete:
builtins are embedded in the running binary, while project overrides are loaded
from `.odx/topics`. Editing builtin source without rebuilding cannot change the
running binary's effective policy. Local replacement replaces the entire topic.

A temporary project with `pkg/a.odin`, edge role and explicit allocators off was
rendered before/after changing `errors.types` from `Error` to `Failure` and adding
`odin.flags: ["-strict-style"]`. `cmp` reported identical generated bytes. Adding
an unmapped `other/a.odin` also produced identical bytes. A fresh build from the
current source produced identical output to the existing binary, using:

```sh
/Users/ratiu5/.local/share/mise/installs/odin/dev-2026-09/odin build odx \
  -out:/tmp/odx-m4-freshness.Cvr9qS/odx-fresh \
  -vet -strict-style -warnings-as-errors -vet-packages:odx
```

These are meaningful counterexamples: error inference, compiler configuration,
and the population of packages can change without the current rendering changing.
Byte comparison alone cannot detect unrepresented policy inputs. Conversely,
routine edits inside an existing source file need not stale policy guidance: this
document is an instruction set, not certification of current findings.

## Input inventory

| Input | Effect and freshness treatment |
| --- | --- |
| Effective builtin topics embedded in the binary | Statements, rule specs, severity, rationale, discouraged behavior, advice, applicability; include effective values, not working-tree `rules/` bytes. |
| `.odx/topics/<topic>/topic.md` and `*.odx.md` | Added/removed topics and whole-topic overrides change effective rulebook; include effective parsed content. |
| Rule check fields | Every accepted selector field changes enforcement; scope prose alone does not encode call names, parameter requirements, import patterns, attributes, etc. Include normalized complete specs. |
| Rule status and metadata | Retired and disabled status, severity, ignorable/baselineable and identity affect interpretation; avoid silently hashing only statements. |
| `roles`, `default_role`, `exclude` | Determine package domain and applicability; sorted discovered package path/role inventory makes that domain explicit. |
| `disabled` | Changes effective rules; reasons can matter to human policy review even where findings do not change. |
| `dependencies` | `may_import` and `deny`, including load-time defaults, change architecture policy without changing check kind or role labels. |
| `errors.types` | Changes compiler-entity inference; current renderer omits it. |
| `odin.explicit_allocators` | Changes vet-tag applicability; current scope description already reflects it. |
| `odin.flags`, collections, custom attributes and allowed vet disables | Change compiler evidence, import resolution or permitted directives; include effective configuration. |
| `odin.path`, version | Configured compiler identity changes policy's declared toolchain. Actual executable selected by environment is run evidence, not static instruction freshness unless generation starts consulting it. |
| Forbidden/required flags, declined flags, tagged-files minimum | Doctor policy; include if generated guidance promises the effective project policy. Hashing the complete loaded Config is a simple conservative choice. |
| Discovery state | Adding/deleting/renaming packages, directory exclusion changes, symlink handling, nested config errors and role overlap can change domain or make it invalid. Re-run normal project discovery/validation on every generation/freshness request. |
| Requested scope | Whole-project versus one package, normalized root-relative package path; equivalent absolute/relative spellings should render identically. |
| Generator contract | Render/version marker and renderer bytes identify formatting changes. A separate format version covers policy-interpreter changes that do not naturally change rendered text. No current general odx version constant exists. |
| Human Markdown outside the owned block | Must neither affect freshness nor be rewritten during regeneration. |
| Baseline and source suppressions | Affect findings and exits, not what policy asks authors to write; explain their effect generically rather than hashing live debt. |
| Rule examples and prose omitted by the renderer | Not inherently inputs to abbreviated guidance, unless used to assert rule semantics. Include any material used to generate displayed corrective guidance. Local example directories affect executable trials, not current instruction selection. |

## Alternatives and recommendation

1. Raw file hashes are easy to implement but cause churn for comments/formatting,
   require complete discovery of all files, confuse embedded builtin policy with
   editable source, and must separately add scope/package discovery/tool versions.
2. Deterministic rendering and byte comparison is transparent, naturally catches
   renderer changes and avoids timestamp machinery. It is insufficient unless
   every relevant semantic input is displayed or included as normalized metadata.
3. Recommended: deterministic rendered owned block with effective-policy snapshot
   metadata, then exact byte comparison. Serialize loaded Config, selected
   package/role inventory and normalized effective rule contracts using sorted map
   keys. This can be readable fenced JSON or a compact digest. A digest is only a
   freshness mechanism; readable selector/config descriptions remain necessary to
   make guidance accurate. Do not hash absolute project root or runtime rule file
   paths. Sort set-like values only where order is semantically irrelevant;
   preserve compiler argument order.

Use the same renderer for stdout, freshness comparison and explicit updates.
No compiler execution or AST parse is needed for these static policy documents.
The existing package discovery cost is sufficient; no cache or persisted input
index is justified. Revisit a digest/cache only if measured document size or
generation time becomes a problem.

The mise library has a direct API without external commands:
`crypto_hash.hash_bytes(.SHA256, serialized_snapshot, context.temp_allocator)`
from `core:crypto/hash`, then `hex.encode(digest, context.temp_allocator)` from
`core:encoding/hex`. Alternatively `core:crypto/sha2` supplies `Context_256`,
`init_256`, `update`, and `final` for a fixed 32-byte buffer. JSON marshal already
supports `sort_maps_by_key = true` in this repository. Do not serialize the whole
runtime Topic unchecked: `exemplar` concatenates directory-walk results without
sorting, and runtime `Rule.file` paths/source fields are implementation locations.
Use a dedicated semantic snapshot or cloned topics with unused exemplar/runtime
fields omitted. Include a generator contract revision. `ODX_ODIN` overrides the
compiler when checking, but generation does not invoke it; label any displayed
toolchain settings as configured settings and avoid implying a compiler run.

## Proposed command and ownership contract

Provide vendor-neutral Markdown emission and keep `--emit-claude-md` as a
compatibility alias. A compact dedicated surface such as
`odx guidance check <document> [--path <package>]` and
`odx guidance update <document> [--path <package>]` makes read versus write clear;
exact spelling is an implementation decision. Do not silently mutate documents
from `odx check`, `doctor`, freshness checks, or hooks.

Own exactly one block between explicit unique HTML comment markers. Check returns
0 only when its bytes match current expected output; absent/stale block returns 1;
invalid policy, unreadable file, malformed/reversed/duplicate markers returns 2.
Update replaces only that range and preserves exact prefix/suffix bytes. Missing
block may append a new block, including to a newly created file. Reject malformed
ownership rather than guessing. Existing unmarked `## odx` sections are ambiguous:
explain manual marker migration; do not infer ownership up to an arbitrary heading
and accidentally erase human text. AGENTS.md and CLAUDE.md are ordinary target
filenames; Markdown consumption must not be part of enforcement correctness.

For safe writes, the mise `core:os` exposes `create_temp_file`, `write`, `close`,
and `rename`. `write_entire_file` truncates by default, so a same-directory temp
file plus rename is preferable when preserving a human document matters. Preserve
permissions as appropriate, reject directories and ambiguous/symlink targets if
necessary, and report filesystem errors explicitly. Atomic replacement behavior
must be validated on supported platforms rather than asserted universally.

## Acceptance cases to implement

- Fresh check is non-mutating; explicit update followed by check is clean; repeated
  update is byte-idempotent; human prefix/suffix remain byte-identical.
- Local override and disabled rule changes stale output; same-value JSON5
  whitespace/comments do not if normalized semantic metadata is selected.
- Dependency deny, error type suffix, compiler flag, selector name, severity and
  newly applicable role/package changes stale output even if statement is unchanged.
- Equivalent map insertion order and root-relative/absolute selection produce the
  same block; sibling path selection cannot pass against the wrong package block.
- Source body edit with unchanged discovery/policy does not require regeneration.
- Missing, repeated, reversed, partially deleted and embedded marker text fail
  predictably without modifying the file. Empty project remains a labeled catalog.
- Builtin source edits require rebuild; effective builtin changes then stale the
  old block. A pinned old binary remains authoritative only for its own policy.
- This research establishes the observed pre-change gap and a bounded design;
  freshness commands, write safety and cross-platform behavior remain unproven
  until implementation tests run.
